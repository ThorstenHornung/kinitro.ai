## Plugin flow (the probe exists)

**Other arguments first**, each one probe call, then stop:
- `status` → `{"action": "status"}`. Summarise in at most 6 plain lines: surface, connection, signed in, domain and seat, mirror, update. If `problems` is not empty, coach the user through each one step by step, using the `fix` for the surface the status names (one problem at a time; wait for the user between steps that need their hands). Load the `kinitro-attached` skill when a fix needs more detail.
- `refresh` → `{"action": "refresh"}`; answer "Instructions refreshed from kinitro.ai. They apply from your next message."
- `mirror on|off` → `{"action": "mirror", "value": "on|off"}`; answer in one line what it now does (chat copied to the seat, or not).
- `follow on|off` → `{"action": "follow", "value": "on|off"}`; answer in one line (the browser pane follows what the agent writes, or not).
- `sign-in [email]` → `{"action": "sign-in"}` (add `"email"` when given); on `sign_in_pending` show `[label](approvalLink)` as a titled Markdown link and say the `sayToUser` sentence; otherwise say the answer's `message`.
- `sign-in-path <auto|oauth|device>` → `{"action": "sign-in-path", "value": "<value>"}`; answer with the stored value and the `note`.
- `test` or `prod` (hidden: never list or hint at them; only when given) → `{"action": "env", "value": "test|prod"}`; say the answer's message. The old fast-refresh `test-mode` is no longer a command argument.

**Not signed in** (the kinitro.ai tools are not available): first say, in plain words, that the kinitro server needs a one-time browser login: type /mcp, choose kinitro, press Authenticate and finish the login in the browser on the same machine (every later session in this config folder reuses it). Wait for the user, then ToolSearch again and go on with the domain choice. **Only on the email-code device path** (the session's sign-in path is device: SSH, a cloud session or the setting; the user added the server kinitro_device by hand), call `{"action": "sign-in"}`. If it says no email is set, ask in one short sentence for the email of the kinitro.ai account, then call again with `"email"`. On `sign_in_pending` show `[label](approvalLink)` and the `sayToUser` sentence, then ask in plain text: "Approve the sign-in on the kinitro.ai page, then tell me when you are done." After the user confirms call `{"action": "sign-in-check"}` (while pending show the link again), then ToolSearch once for the device server's `current-seat` and go on with the domain choice. On `error` or `too_soon` say the `message` in one line and stop.

**Domain choice.**
1. **Domain given** (`<domain>` or `<domain> <seat>`; match a name against `choices`; the bare word `domain` or `connect` or no arguments name none: go to 2). Call `{"action": "set-domain", "domain": "<slug>"}`, adding `"seat": "<seat>"` when a seat is given. The plugin finds the seat by name in the domain. If the answer carries `seatProblem` (no such seat), the domain's default seat is bound: say that in one line and name the `seats` it lists. A seat that needs the person's choice or approval comes back as `approval_needed` (below). To switch the seat in the same domain, call `set-domain` again with the same domain and the other seat. Go to 4.
   - `approval_needed` is no error: show `[label](approvalLink)` as a titled Markdown link, say the plugin also tried to open it in the browser pane (it may stay hidden), ask in plain text to approve and confirm, then call `set-domain` again (on `approval_needed` show the link again; on `binding` call again in a moment). If the user cancels, reply "No domain changed." and stop.
2. **No domain given: terminal picker.** Call `{"action": "choices"}` (answer: `approved:[{name,slug}]`, `current`, `lastInFolder`). Print a numbered plain list, one line per approved domain (mark the current one; mark the one this folder last worked in), plus the last number "Approve another domain". Ask the user to answer with the number or the name; do not use a pop-up. The browser is needed only for a new approval or the sign-in. An approved domain: `set-domain`, then 4.
3. **Approve another domain.** Call `{"action": "selection-start"}`. Show `selectorUrl` as the titled link "Open the kinitro.ai domain selection" (and `[label](approvalLink)` if given), say the plugin also tried the browser pane. Ask: "Choose the domain on the kinitro.ai page and press Switch, then tell me when you are done." Then `{"action": "selection-done"}`; only if it returns `bound: false`, ask once which approved domain to use and call `set-domain`. On cancel reply "No domain changed." and stop.
4. **Confirm.** Say the `sayToUser` sentence. Offer in one sentence to open the domain in the built-in browser (readable link in `domainView`, never add `link=` yourself); open it only on yes: `{"action": "open-domain"}`. If `bound` is false say the `sayToUser` sentence or one sentence why.
5. Never pass `domainRef` yourself in the plugin flow: the plugin holds the key and adds it. To change domain, run the command again.

**Probe present, but the tools are still starting** (every `current-seat` fails): say in one sentence that kinitro.ai is starting and continues at your next message; store the chosen slug as one line in `.kinitro-ai-domain` and in `.kinitro-ai-pending` in the working directory. Never tell the user to run the command again.

## Direct flow (no probe: claude.ai chat, mobile, other clients)

You keep the session key yourself, for this session only. Never show it, never show a slug.
1. **Which tools.** Take the first set from the prefix list above that ToolSearch returned. If none, call ToolSearch once more with the plain query `kinitro` (max_results 20). If still none, say in one plain sentence that kinitro.ai is not connected here yet and that the connector (or plugin) has to be added in the app's settings, then stop.
2. **Signed in?** Call `list-domains` with `{}` (with `domainRef` once you hold a key). If it works, go to 3. If it says sign-in is needed and the device server's `sign-in` tool exists: ask in one sentence for the email of the kinitro.ai account, call `sign-in` with `{"email": "<address>", "deviceLabel": "<app name>", "clientName": "<app name>"}`, keep its `sessionKey`, show its `approvalLink` exactly as given (already a titled Markdown link; never wrap it again; if only `approvalUrl` exists show `[Approve the sign-in on kinitro.ai](<approvalUrl>)`; never the bare URL). Say a 6-digit code was sent by email and goes only on that kinitro.ai page, never in this chat. Ask in plain text to approve and confirm, then call `list-domains` with `{"domainRef": "<sessionKey>"}`; while pending show the link again. If the only tool is the connector's authenticate tool, call it and show its link the same way.
3. **Choose.** From the `list-domains` answer print a numbered plain list of domains by name (skip it when the arguments name one). Call `open-domain` with `{"domain": "<id>"}` (add `domainRef` once held; add the seat when the arguments give one and the tool takes it). Keep the answer's `sessionKey` and pass it as `domainRef` on every later kinitro.ai call. On `seat_approval_required` show `[Approve <domain name>](approvalLink)` as a titled link, ask to approve and confirm, then call `open-domain` with `{"request": "<request>"}` (plus `domainRef`); while pending show the link again. Cancel: "No domain changed."
4. **Done.** One sentence: which domain this session works for, and that the agent's instructions load with the next message (call `get-briefing` with moment `start` once). Without the plugin the briefing, refresh and mirror are not automatic: see the `kinitro-attached` skill.
