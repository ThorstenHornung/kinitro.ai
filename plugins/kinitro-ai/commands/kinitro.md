The user wants to choose the kinitro.ai domain this Claude session works for. Arguments: "$ARGUMENTS". No arguments at all (a bare `/kinitro`) mean `domain`, and `connect` is a synonym of `domain`: both go to the domain choice (sign in first when needed).

The kinitro.ai tools are the plugin's own, on its device server: `mcp__plugin_kinitro-ai_kinitro_ai_device__<verb>` (the older `mcp__plugin_kinitro-ai_kinitro_ai__<verb>` only for a user who chose the OAuth path). Below, "the kinitro.ai tools" and `<verb>` mean these; the plugin's own `mcp__kinitro-ai__probe` is a different tool and keeps its name. With the plugin's probe, never use another kinitro.ai connection (`mcp__kinitro_ai__<verb>`, `mcp__claude_ai_Kinitro__<verb>`): the probe works only with the plugin's own. Without the probe (the Claude desktop app runs no plugin hooks, so the probe never exists there), follow **Direct flow** below, which may use the account connector too. If the plugin's kinitro.ai tools are not available (not connected yet: the first run), never send the user to /mcp or to a browser callback: the plugin signs in by email code, which needs no localhost address. If `mcp__kinitro-ai__probe` is available, sign in yourself: follow **First sign-in** below. If it is not, follow **Direct flow** below.

**First sign-in** (the kinitro.ai tools are not available, the probe is): call `mcp__kinitro-ai__probe` with `{"action": "sign-in"}`. If the answer says no email is set, ask the user in one short sentence for the email address of their kinitro.ai account (never a password or a code), then call it again with `"email": "<address>"`. On `status: "sign_in_pending"` show `[label](approvalLink)` as a Markdown link and say the `sayToUser` sentence, then ask with AskUserQuestion: "Approve the sign-in on the kinitro.ai page, then confirm here." Options "I approved it" and "Cancel" (reply "Not signed in." and stop). On "I approved it" call `{"action": "sign-in-check"}` (while still pending show the link again), then call ToolSearch once with `{"query": "select:mcp__plugin_kinitro-ai_kinitro_ai_device__current-seat", "max_results": 3}` to load the sign-in's tools and continue straight into the domain choice below (step 1 or 2) with the arguments as given. On `status: "error"` or `"too_soon"` say the answer's `message` in one line and stop.

Talk to the user in their language and call it "domain" (German: "Arbeitsbereich"); never say "slug".

**`update`** (the arguments are `update`): do not load or call any kinitro.ai tool. Run these two commands with the Bash tool, one after the other, exactly as written: `claude plugin marketplace update kinitro-ai`, then `claude plugin update kinitro-ai@kinitro-ai`. If the first one fails, do not run the second. Then answer in the user's language: the version the second command reports (or that kinitro-ai is already up to date), and "Run /reload-plugins to load the new version in this session." If a command fails, quote its error in one line and add: "In Cowork or the Claude desktop app, re-upload the plugin from https://methos.kinitro.ai/download/plugins/claude/." Then stop.

Work in this order, without commentary between calls. The plugin stores the choice and opens pages in the browser pane (the internal browser) itself.

0. **Load the tools first.** Call ToolSearch once with `{"query": "select:mcp__kinitro-ai__probe,mcp__plugin_kinitro-ai_kinitro_ai__current-seat,mcp__plugin_kinitro-ai_kinitro_ai_device__current-seat,mcp__plugin_kinitro-ai_kinitro_ai__list-domains,mcp__plugin_kinitro-ai_kinitro_ai__open-domain,mcp__plugin_kinitro-ai_kinitro_ai_device__sign-in,mcp__plugin_kinitro-ai_kinitro_ai_device__list-domains,mcp__plugin_kinitro-ai_kinitro_ai_device__open-domain,mcp__claude_ai_Kinitro__list-domains,mcp__claude_ai_Kinitro__open-domain,mcp__claude_ai_Kinitro__current-seat,mcp__kinitro_ai__list-domains,mcp__kinitro_ai__open-domain,mcp__remote-devices__Claude_Browser__preview_start,mcp__Claude_Browser__preview_start", "max_results": 20}`. (ToolSearch needs to find only the names that exist; the others are simply not returned.) **If `mcp__kinitro-ai__probe` is returned**, go on with the steps below. **If it is not returned, do not wait for it and do not retry for it**: the Claude desktop app never has it. Go straight to **Direct flow**, in the same turn, with no commentary and no question to the user about routes.

**Other arguments first:** `refresh` → call `mcp__kinitro-ai__probe` with `{"action": "reload"}` and answer "Instructions refreshed from kinitro.ai." · `test` → `{"action": "test-mode", "value": "on"}`, answer "Test mode on: instructions refresh every 2 minutes." · `test off` → `{"action": "test-mode", "value": "off"}`, answer "Test mode off: instructions refresh daily." · `status` → `{"action": "status"}`, summarise in three lines (domain, instructions loaded at, refresh mode) without codes or ids. · `sign-in` (optionally followed by an email address) → `{"action": "sign-in"}`, with `"email": "<address>"` when one is given; on `status: "sign_in_pending"` show `[label](approvalLink)` as a Markdown link and say the `sayToUser` sentence; otherwise say the answer's `message` in one line. Never ask for a password or for the code, and never repeat a code the user typed here. · `sign-in-path <auto|oauth|device>` → `{"action": "sign-in-path", "value": "<value>"}`, answer with the stored value and the answer's `note`. Then stop.

1. **Domain given** (the arguments name a domain, by slug such as `verum` or by name; match it against `choices` if it is a name; the bare words `domain` and `connect`, and empty arguments, name none: go to step 2): call `mcp__kinitro-ai__probe` with `{"action": "set-domain", "domain": "<slug>"}` and go to step 4.
   - **Approval needed** (the answer has `status: "approval_needed"`, also from `selection-done` or the `pending` entry of `choices`): this is no error. Show `[label](approvalLink)` as a Markdown link, say the plugin also tried to open it in the browser pane (it may stay hidden), and ask with AskUserQuestion: "Approve <domain> on the kinitro.ai page, then confirm here." Options "I approved it" (call `set-domain` with the same slug again; on `approval_needed` show the link again) and "Cancel" (reply "No domain changed." and stop). On `status: "binding"` call `set-domain` again in a moment.
2. **Ask which domain.** Call `mcp__kinitro-ai__probe` with `{"action": "choices"}`. Ask with AskUserQuestion: "Which domain should this session work for?" Options: one per entry in `approved` (label = name; description = "current" for the `current` one, else "approved"), plus "Approve another domain" (description = "opens the kinitro.ai domain selection").
   - An approved domain: call `set-domain` with its slug and go to step 4.
3. **Approve another domain.**
   - Call `mcp__kinitro-ai__probe` with `{"action": "selection-start"}`. Always show the returned `selectorUrl` as the Markdown link "Open the kinitro.ai domain selection" (and `[label](approvalLink)` when it returns one), and say the plugin also tried to open it in the browser pane, which may stay hidden.
   - Ask with AskUserQuestion: "Choose the domain on the kinitro.ai page and press Switch. Then confirm here." Options: "Confirm my choice" (description = "use the domain I switched to") and "Cancel".
   - "Confirm my choice": call `mcp__kinitro-ai__probe` with `{"action": "selection-done"}`. Only if it returns `bound: false`, ask once which approved domain to use and call `set-domain`.
   - "Cancel": reply "No domain changed." and stop.
4. **Confirm:** reply with the `sayToUser` sentence, then offer in one sentence to open the domain in the built-in browser, with the readable link in `domainView` (the plugin gives it without the `link=` part; never add that part yourself). Open it only if the user says yes: `mcp__kinitro-ai__probe` with `{"action": "open-domain"}`. Never show slugs, node codes, ids, session ids or file paths. If `bound` is false, say the `sayToUser` sentence if there is one, else one sentence why.
5. Never pass `domainRef` yourself: the plugin keeps this session's key and passes it on every call of the kinitro.ai tools. Never ask for, show or repeat a session key. To work in another domain, run this command again; the domain is added to the same session.

**Direct flow** (the probe is not available: the Claude desktop app, or a terminal where the plugin has not started; no plugin hooks run, so nothing keeps the session key for you: you keep it yourself). Do this in the user's language, ask nothing about routes, and never show the session key or a slug.
- **Which tools.** Take the first set that ToolSearch returned: the plugin's own (`mcp__plugin_kinitro-ai_kinitro_ai__<verb>`), the plugin's device server (`mcp__plugin_kinitro-ai_kinitro_ai_device__<verb>`), then the kinitro.ai account connector (`mcp__claude_ai_Kinitro__<verb>`), then `mcp__kinitro_ai__<verb>`. Use the connector only if it belongs to this plugin's environment (a connector named Kinitro Test belongs to the Test build, one named Kinitro to the Production build). If none was returned, call ToolSearch once more with the plain query `kinitro` (max_results 20); if still none, say in one plain sentence that kinitro.ai is not connected in this app yet and that the plugin has to be installed or switched on in the app's plugin settings, then stop.
- **Signed in?** Call `list-domains` with `{}`. If it works, you are signed in: go on at **Choose**. If it answers that sign-in is needed (or the tool is only an authenticate tool), and the device server's `sign-in` tool exists: ask the user in one short sentence for the email address of their kinitro.ai account (never a password or a code), call `sign-in` with `{"email": "<address>", "deviceLabel": "Claude desktop app", "clientName": "Claude desktop app"}`, keep the `sessionKey` of the answer for this session only, show `[Approve this sign-in](approvalLink)` as a Markdown link (the answer's `approvalLink`, or `approvalUrl`), say: a 6-digit code was sent to the address; type it only on that kinitro.ai page, never in this chat. Then ask with AskUserQuestion: "Approve the sign-in on the kinitro.ai page, then confirm here." Options "I approved it" and "Cancel" (reply "Not signed in." and stop). On "I approved it" call `list-domains` with `{"domainRef": "<sessionKey>"}`; while it still says pending show the link again. If the only kinitro.ai tool is an authenticate tool of the connector, call it and show its link the same way.
- **Choose.** From the `list-domains` answer ask with AskUserQuestion: "Which domain should this session work for?" (one option per domain by name; if the arguments name a domain, match it and do not ask). Then call `open-domain` with `{"domain": "<id of the domain>"}` (add `"domainRef": "<sessionKey>"` when you hold a key). Keep the answer's `sessionKey` for this session only and pass it as `domainRef` on every later kinitro.ai call. If the answer is `seat_approval_required` (an approval link and a `request`): show `[Approve <domain name>](approvalLink)` as a Markdown link, ask "Approve <domain name> on the kinitro.ai page, then confirm here." with options "I approved it" and "Cancel" (reply "No domain changed." and stop); on "I approved it" call `open-domain` with `{"request": "<request>"}` (and `domainRef` when held); while it is still pending show the link again.
- **Done.** Say in one sentence which domain this session works for and that the agent's instructions load with the next message. Never show slugs, node codes, ids or the session key.

**Probe, but the tools are still starting** (only when the probe was returned but `current-seat` of every set fails): say in one plain sentence that kinitro.ai is starting and that it continues by itself at your next message; store the chosen slug as one line in `.kinitro-ai-domain` and in `.kinitro-ai-pending` in the working directory (the plugin opens the session at the next message). Never tell the user to run the command again.
